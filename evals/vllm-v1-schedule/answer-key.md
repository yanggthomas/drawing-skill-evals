# G1 answer key — one `Scheduler.schedule()` step (vLLM V1 @ 4c2d277)

Paths are relative to `src/`, so `scheduler.py` means `src/vllm/v1/core/sched/scheduler.py`. Each fact describes a mechanism a diagram can show. The correctness grader's rubric includes the same nine facts.

1. **Budget source.** The step starts with one token budget, `token_budget = max_num_scheduled_tokens`. That value defaults to `max_num_batched_tokens` and is shared by every request scheduled in the step. (`scheduler.py:133-137`, `scheduler.py:583`)
2. **Budget decrement.** Each scheduled request takes `num_new_tokens` off the budget, whether it came from running (`scheduler.py:826`) or waiting (`scheduler.py:1315`). Both loops stop once the budget reaches 0. (`scheduler.py:631`, `scheduler.py:886`)
3. **Running before waiting.** The step first walks the `running` list in order (`scheduler.py:631`). Only after that does it admit requests from the `waiting` queue (`scheduler.py:873-888`).
4. **Chunked prefill.** A request's `num_new_tokens` is the gap between its tokens and its `num_computed_tokens`. The scheduler caps it by `long_prefill_token_threshold` and then by the remaining budget, so a long prompt gets only a chunk this step (`scheduler.py:675-684`, `scheduler.py:1085-1125`). After scheduling, `num_computed_tokens` is advanced by the scheduled count, so the next step continues the prompt where this chunk stopped (`scheduler.py:1598`). There is no separate prefill or decode phase: a decode is the same rule with a gap of 1 (`scheduler.py:566-575`).
5. **KV block allocation.** Before a request is committed to the step, `kv_cache_manager.allocate_slots(request, num_new_tokens, ...)` reserves KV-cache blocks for the new tokens. It returns `None` when there are not enough free blocks. Running requests: `scheduler.py:748`. Waiting requests: `scheduler.py:1211`.
6. **Preemption (running side only).** When allocation fails for a running request, the scheduler preempts a victim and retries. The victim is the last request in `running` (FCFS), or the lowest-priority request under the priority policy (`scheduler.py:764-804`). `_preempt_request` frees the victim's KV blocks, sets it to `PREEMPTED` with `num_computed_tokens = 0`, and puts it back at the **front** of the waiting queue (`scheduler.py:1540-1583`). If the victim is the current request itself, that request is not scheduled this step (`scheduler.py:812-818`).
7. **Preemption blocks admission.** If any request was preempted in this step, the waiting queue is skipped entirely: `if not preempted_reqs` (`scheduler.py:874`).
8. **Admission stop conditions.** A waiting request is admitted only while all of these hold: the budget is > 0, the queue is non-empty, and `len(running) < max_num_active_reqs`. Its `allocate_slots` call must also succeed, and a failure there **stops** admission without preempting anyone (`scheduler.py:886-895`, `scheduler.py:1225-1232`). On admission the request first takes its prefix-cache hit as already-computed tokens, so only the uncached suffix is scheduled (`scheduler.py:938`, `scheduler.py:1085`). The request then moves into `running` with status `RUNNING` (`scheduler.py:1294`, `scheduler.py:1316`).
9. **Output to the model runner.** The step returns a `SchedulerOutput` (`scheduler.py:1463`, `output.py:232-263`) carrying:
   - `scheduled_new_reqs`: full `NewRequestData` (prompt tokens and block ids) for requests scheduled for the first time.
   - `scheduled_cached_reqs`: a `CachedRequestData` diff (new block ids, `num_computed_tokens`) for continuing running requests and resumed preempted requests.
   - `num_scheduled_tokens`: tokens per request, plus `total_num_scheduled_tokens`.
   - `finished_req_ids` and `preempted_req_ids`, so the workers can free their cached state.
