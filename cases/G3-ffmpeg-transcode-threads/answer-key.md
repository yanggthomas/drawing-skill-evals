# G3 answer key — the threaded transcoding pipeline in `fftools` (FFmpeg master)

Paths are relative to `src/fftools/`; `S` = `ffmpeg_sched.c`, `SH` = `ffmpeg_sched.h`, `TQ` = `thread_queue.c`. Each fact describes a mechanism a diagram can show; the correctness grader's rubric includes the same 8 facts without the line references.

1. **Scheduler in the middle.** Demuxers, decoders, filtergraphs, encoders and muxers never talk to each other directly. Every send and receive goes through the `Scheduler`, which is the only object that knows the whole graph (a DAG, checked at start) (`SH:26-70`, `S:1589`).
2. **One thread per component.** Each demuxer, decoder, filtergraph, encoder and muxer runs in its own thread: `input_thread`, `decoder_thread`, `filter_thread`, `encoder_thread`, `muxer_thread` (`ffmpeg_demux.c:843`, `ffmpeg_dec.c:909`, `ffmpeg_filter.c:3443`, `ffmpeg_enc.c:1009`, `ffmpeg_mux.c:403`). `sch_start` creates them muxers first and demuxers last (`S:404-424`, `S:1741-1801`).
3. **Queues sit at the consumer's input.** Queues: each decoder has a packet queue, each filtergraph a frame queue (one stream per input plus a control stream), each encoder a frame queue, each muxer a packet queue with one stream per output stream. The demuxer has no input queue (`S:802`, `S:846`, `S:894`, `S:1703`).
4. **Data path.** Packets go demux → decoder → frames → filtergraph → encoder → packets → muxer. For stream copy, demuxed packets go straight to the muxer. Subtitle frames skip filtering and go decoder → encoder (`SH:28-50`).
5. **Thread loop.** Each worker thread loops: receive from its own input queue (`sch_*_receive`), process, then send downstream (`sch_*_send`, which pushes into the next thread's queue) (`ffmpeg_dec.c:924`/`999`, `ffmpeg_filter.c:3473`/`2792`, `ffmpeg_enc.c:1037`/`540`, `ffmpeg_mux.c:422`).
6. **Bounded queues = backpressure.** Queues are tiny (2 entries by default for packets and for frames), and `tq_send` blocks while the destination is full. A slow consumer therefore stalls its producers (`SH:257`, `SH:262`, `TQ:163-164`).
7. **Sync by muxer DTS.** Each packet that reaches a muxer stream updates that stream's `last_dts` and calls `schedule_update_locked`. That function finds the trailing output DTS and unchokes only the sources (demuxers / source filtergraphs) feeding streams that are less than `SCHEDULE_TOLERANCE` (100 ms) ahead of it. At least one source always stays unchoked (`S:2009-2066`, `S:1422-1520`, `S:45`).
8. **Choking a demuxer.** A choked demuxer blocks on a condition variable in `waiter_wait` at the start of `sch_demux_send`. Choking it also chokes the queues it feeds (`tq_choke`), so downstream threads don't drain them (`S:320-337`, `S:1392-1420`, `S:2179-2199`).
